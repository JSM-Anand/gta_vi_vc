    ## How Does the Site Scale?

    Here's something Claude picked up from the live site that you'd probably never notice yourself.

    The whole layout scales with the width of the window. Not in breakpoints that jump. Continuously.

    The site uses one layout unit, and everything, text, padding, button sizes, is a multiple of it:

    ```css
    :root {
      --u: calc(4vw / 3);

      @variant lg {
        --u: calc(8vw / 7);
      }
      @variant hd {
        --u: 1vw;
      }
    }
    ```

    So a button isn't `48px` tall. It's `calc(var(--u) * 3.5)`. Make the window wider, the whole hero grows with it, and it stays in proportion.

    That's why a clone built with fixed pixel sizes looks right at exactly one screen width, and slightly off everywhere else.

    ## A Small Tailwind Gotcha

    And while building this, we hit a nice little Tailwind v4 trap.

    The live site's layout changes at 1440px. So Claude first wrote `min-[1440px]:` classes.

    They were ignored.

    Arbitrary pixel breakpoints get sorted before the built-in rem breakpoints, so the `lg` styles were winning. The fix was to register 1440px as a proper breakpoint:

    ```css
    --breakpoint-hd: 90rem;
    ```

    Now `hd:` sorts correctly after `lg:`.

    I'm showing you this not because you need to memorise it, but because it's a good example of what to look for. Claude wrote the class, **checked the result**, saw it wasn't applying, and found out why. That's the loop you want.

    ## "Keep It Up Until the Images Have Loaded"

    That part of the prompt matters more than it looks.

    Lots of loaders just wait a fixed number of seconds. That's a lie to the user. On a fast connection they wait for nothing. On a slow one, the loader disappears and they watch images pop in.

    Ours waits for the real thing:

    ```jsx
    Promise.all([
      document.fonts.ready,
      ...imgs.map((img) => img.decode().catch(() => {})),
    ])
    ```

    Every hero image decoded, every font ready.

    And then one more detail. It doesn't cut off mid-sweep. It waits for the light to **finish its current pass** before it fades out.

    ```jsx
    shine.current.addEventListener('animationiteration', () => setReady(true), { once: true })
    ```

    That's the difference between a loader that disappears and one that **ends**.

    ## When the First Approach Doesn't Work

    Here's where it gets interesting.

    The obvious way to build this is with normal HTML images and CSS. Each collage piece is an image, GSAP scales it, and the logo reveal is a CSS mask.

    Except the images are AVIF files. And in Chrome, AVIF images don't work as a CSS `mask-image`. The reveal just didn't render.

    So Claude went and looked at how the live site actually does it.

    And it turns out Rockstar doesn't use HTML images for this animation at all. **It's drawn on a canvas.**

    So we did the same thing.

    ## How the Canvas Version Works

    GSAP doesn't have to animate DOM elements. It can animate any JavaScript object.

    So we keep a plain state object, a number for each piece of the collage, and let GSAP tween those numbers:

    ```js
    tween(state.gta, { p: 1, ease: 'power3.out' }, 1.06, 2.05)
    tween(state.gta, { wipe: 1, ease: 'power1.out' }, 1.11, 3.24)
    ```

    Then on every frame, GSAP's ticker redraws the canvas from that state:

    ```js
    gsap.ticker.add(renderer.render)
    ```

    Each piece flies in "from the camera", drawn at a scale of `1 / p` while `p` eases towards 1. And the "Grand Theft Auto" wordmark reveals top to bottom with a soft gradient edge, painted onto an offscreen canvas.

    And look at those numbers. `1.06`. `2.05`. `3.24`.

    Those aren't round numbers somebody picked because they felt nice. Every start time, end time and ease was **measured** from the live site and fitted to the closest GSAP ease. Nine collage pieces, each with its own timing.

    That's why this part looks right instead of almost right.

    ## Then Hand It Back to Normal HTML

    Once the animation finishes, the canvas fades into the static poster and stops drawing:

    ```js
    tween($('poster'), { autoAlpha: 1, ease: 'none' }, 3.63, 4.13)
    tl.call(finish)
    ```

    So for the remaining 99% of the time someone's on the page, it's just regular images. No canvas burning CPU in the background.

    And if someone has reduced motion turned on in their system settings, the canvas never runs at all. They get the finished poster immediately.

    ## What Is ScrollTrigger Doing?

    Two things.

    **Pin** keeps the hero fixed in place while you keep scrolling.

    **Scrub** ties the animation to the scrollbar. Instead of playing over time, the animation's progress **is** your scroll position. Scroll halfway, it's halfway. Scroll back up, it plays in reverse.

    ```js
    const tl = gsap.timeline({
      scrollTrigger: {
        trigger: '#hero',
        start: 'top top',
        end: '+=100%',
        pin: true,
        scrub: true,
      },
    })
    ```

    That's the core of almost every "scroll animation" site you've ever seen.

    ## "Shrinks a Little and Fades" Was Never the Full Story

    Here's the uncomfortable part.

    Claude built exactly what I asked for in lesson 7. "It stays pinned while the poster shrinks a little and fades out." That's what we got.

    The problem was **my description**.

    When Claude went through the recording frame by frame, this is what was actually happening:

    - the whole hero shrinks to 90%
    - the poster, date, button and badges fade out
    - but the logo **lingers**, and fades out more slowly than everything else
    - the cursor glow fades away
    - a Pre-Order pill appears in the navbar once the hero's button is gone
    - and the next section is already fading in **underneath** the hero

    Five or six things, overlapping, each with its own timing. I described one of them.

    That's the lesson of this whole video in one moment. **A recording carries information you don't even know you're leaving out.**

    ## One Timeline, Many Tracks

    The new version puts all of that on one scrubbed timeline:

    ```js
    tl.to('[data-scroll="content"]', { scale: 0.9, ease: 'none', duration: 0.556 }, 0)
      .fromTo('[data-scroll="content"]', { '--hero-fade': 1 }, { '--hero-fade': 0, ease: 'power3.out', duration: 0.38 }, 0.28)
      .fromTo('[data-scroll="poster-logo"]', { opacity: 1 }, { opacity: 0, ease: 'power3.out', duration: 0.71 }, 0.28)
      .fromTo('[data-scroll="glow"]', { '--scroll-fade': 1 }, { '--scroll-fade': 0, ease: 'none', duration: 0.51 }, 0.35)
    ```

    Look at the logo. It starts fading at the same time as everything else, at 0.28, but takes almost twice as long. That's the "lingering" you feel when you scroll the real site.

    And notice we're tweening **CSS variables** like `--hero-fade`. That lets us fade the text with a CSS filter while GSAP's own opacity tweens still work on the same elements, without the two fighting each other.

    One more change. The pin now uses:

    ```js
    pinSpacing: false
    ```

    Normally, ScrollTrigger adds extra space after a pinned element so the next section waits. Turning that off lets the next section slide in **underneath** the pinned hero, which is exactly what the live site does.

    ## Respect Reduced Motion

    Everything is wrapped in `gsap.matchMedia`:

    ```js
    mm.add({ all: 'all', motion: '(prefers-reduced-motion: no-preference)', mobile: '(max-width: 767px)' }, (ctx) => {
      const { motion, mobile } = ctx.conditions
      ...
    })
    ```

    The fades always run. But the scaling only runs if the user hasn't asked for reduced motion.

    And that `all: 'all'` entry? Without it, the whole block didn't run at all for reduced-motion users, and the page layout broke. One line to make sure the callback always fires. Another thing Claude found by actually testing the reduced-motion case instead of assuming.

    ## Everything Is a Scroll Position

    This section is one long scroll story. And every part of it is tied to a scroll position, measured in screen heights:

    ```
    0.35 → 3.05   scene pinned; image zooms 1.2 → 1
    0.35 → 0.86   image brightens from 20%
    0.50 → 1.19   image fades in
    0.61 → 1.18   title fades in
    0.93 → 1.35   play button fades in
    1.83 → 2.06   cursor glow comes back
    2.05 → 3.05   everything fades out
    2.18 → 3.05   trailer cards grow into place
    ```

    Because it's measured in **screen heights** rather than pixels, it scales properly on any window, just like the live site.

    And to keep all of that readable, there's one small helper:

    ```js
    const scrub = (target, from, to, vars, start, end) =>
      gsap.fromTo(target, from, {
        ...to,
        ...vars,
        ease: vars.ease ?? 'none',
        scrollTrigger: { start: vh(start), end: vh(end), scrub: true },
      })
    ```

    So every line of the animation reads like the table above:

    ```js
    scrub($('image-zoom'), { scale: 1.2 }, { scale: 1 }, {}, 0.35, 3.05)
    scrub($('title'), { opacity: 0 }, { opacity: 1 }, { ease: 'power3.in' }, 0.61, 1.18)
    ```

    ## The Fade-In That Kept Getting Erased

    One gotcha worth knowing if you build anything like this.

    The title fades **in**, and later fades **out**. Two tweens on the same property.

    By default, a `gsap.to` with a ScrollTrigger renders its starting values immediately when the page loads. So the fade-out was overwriting the fade-in before you ever scrolled.

    The fix:

    ```js
    gsap.to(target, { opacity: 0, immediateRender: false, scrollTrigger: { ... } })
    ```

    If you ever have two scroll tweens on the same element and one of them "just doesn't work", check this first.

    ## The Image We Didn't Have

    You could open an image editor and paint in the missing parts yourself. Or you could ask Claude to "just crop it", and lose half the picture.

    Or you let the image itself **grow** to fit the screen.

    ## Generative Fill With Cloudinary

    That's where I use **Cloudinary**.

    Cloudinary hosts your images and videos and delivers them through a URL. And the useful part is that you can change the image just by changing that URL.

    For example, this:

    ```
    ar_9:16,c_pad,b_gen_fill
    ```

    tells Cloudinary to turn the image into a 9:16 portrait, and instead of adding black bars at the top and bottom, to **generate** the missing parts of the scene with AI.

    Same image. Same scene. Just taller.

    **[Recording note: show the desktop image, then the same URL with ar_9:16,c_pad,b_gen_fill added, side by side. Let the extended areas be visible. This is the money shot.]**

    And because it's all in the URL, there's nothing to export, save or re-upload. Want a square version for something else later? Change `9:16` to `1:1`.

    ## One More Thing It Gives You for Free

    While those images are on Cloudinary anyway, add two more things to the URL:

    ```
    f_auto,q_auto
    ```

    `f_auto` picks the best format for each browser automatically, AVIF where it's supported, something else where it isn't. `q_auto` picks the compression so the image still looks the same but weighs less.

    For a page like this, with huge posters and full-screen images, that matters. Remember the final pass is going to check performance. This is one of the easiest wins you'll get there.
