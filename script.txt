- ✅ **01 | Foundations**
    
    So, what is Claude Code?
    
    You can already open Claude, ask it coding questions, give it files and build things with it.
    
    So you might be thinking, "**Why do you need Claude Code?**"
    
    Claude Code can work directly inside your development environment.
    
    You open your project, run Claude Code, and it can read files, search through your codebase, edit code, run terminal commands, use Git, run tests and check whether its own changes actually worked.
    
    Imagine you're building the eCommerce app in this course and customers can add more units to their cart than you actually have in stock.
    
    Instead of finding the cart logic yourself, copying it into Claude and explaining everything around it, you could simply say:
    
    > **Customers can add more units to their cart than we have in stock. Find out why and fix it.**
    > 
    
    Claude can search for the cart logic, inspect your product and inventory code, follow the flow, make the necessary change and run tests afterward.
    
    That's what makes Claude Code an **agentic coding tool**.
    
    The Claude model is still doing the reasoning underneath. Claude Code gives that model the tools, project context and environment it needs to actually work on your code.
    
    That's the important difference.
    
    ## Wait, Can Claude See My Private Code?
    
    Yes.
    
    Claude Code can read files inside the project you've given it access to.
    
    It searches your project locally rather than first uploading and indexing the entire repository somewhere else.
    
    But when Claude needs the contents of a file to reason about your task, relevant information can still be sent to the Claude model.
    
    So, "Claude Code runs locally" does **not** mean "Everything always stays on my machine."
    
    If you're working with private company code, understand the data policy of the account you're using and follow whatever rules your company has around AI tools.
    
    And then there's the obvious next question.
    
    ## What About `.env` Files?
    
    Later this ecommerce app will contain things like:
    
    ```
    DATABASE_URL
    BETTER_AUTH_SECRET
    STRIPE_SECRET_KEY
    ```
    
    You shouldn't assume Claude automatically knows those values are sensitive and will never touch them.
    
    Claude Code has a permissions system where you can explicitly control what it can read, edit or execute.
    
    You can block files such as:
    
    ```
    .env
    .env.*
    secrets/**
    credentials/**
    ```
    
    and control which tools Claude is allowed to use.
    
    You'll set this up properly later in the course.
    
    And you'll actually test it by blocking an environment file, asking Claude to read it and checking that access is refused.
    
    For now, just remember, "**Sensitive files should be explicitly protected.**"
    
    ## How Claude Code Actually Works
    
    Now that Claude can work directly inside your project, how does it decide what to do?
    
    Most tasks follow a simple loop, "**Gather context → Take action → Verify the result**"
    
    Imagine one of your inventory tests starts failing. You ask, "**Find out why the inventory test is failing and fix it.**"
    
    Claude might first run the test.
    
    Then read the error. Then search for the inventory logic. Then inspect the relevant files. Then make a change. Then run the test again.
    
    If it still fails, Claude gets new information from that result and continues.
    
    That's the basic agentic loop.
    
    And while this is happening, you'll actually see the tools Claude is using.
    
    `Read` when it opens a file.
    
    `Glob` when it's looking for files matching a pattern.
    
    `Grep` when it's searching through file contents.
    
    `Edit` when it's changing an existing file.
    
    `Write` when it's creating a file.
    
    `Bash` when it's running something in your terminal, such as:
    
    ```bash
    pnpm build
    pnpm test
    git status
    ```
    
    And if Claude needs information from outside your project, you may see `WebSearch` and `WebFetch`
    
    Later, for example, Claude might use the web to check current Drizzle documentation or research a design reference for the storefront.
    
    So don't only read Claude's final answer. Watch what it's doing.
    
    If you see it reading your product schema while debugging stock, you know what it's investigating. If you see tests running through `Bash`, you know it's verifying its work.
    
    If you see `WebSearch`, Claude decided it needed information outside the project.
    
    And you can interrupt Claude while it's working.
    
    If it makes a wrong assumption or starts heading somewhere you don't want, correct it instead of waiting for the entire task to finish.

    Right now you're using Claude Code interactively.
    
    Running,
    
    ```bash
    claude
    ```

    You give Claude a task, it works, you respond, and the conversation continues.



    - **`claude` keeps the session open.**
    - **`claude -p` runs one task and exits.**

- ✅ **02 | CLAUDE.md**
    
    You've got your `atelier-store` project running now.
    
    But what happens when you close Claude Code and come back tomorrow?
    
    Claude won't automatically remember that you're using `pnpm`, how you're using Drizzle ORM to define your PostgreSQL schemas, or that same mistake you already corrected twice.
    
    You don't want to keep explaining the same project every time you start a new session.
    
    That's where `CLAUDE.md` comes in.
    
    ## So, What Is CLAUDE.md?
    
    `CLAUDE.md` is simply a Markdown file where you give Claude instructions about your project.
    
    Claude loads it automatically when a session starts, so those instructions are already there before you even give it your first task.
    
    For example:
    
    ```markdown
    - Use pnpm instead of npm
    - Use Drizzle for database access
    - Run `pnpm typecheck` before finishing larger changes
    ```
    
    Instead of repeating these things again and again, you put them in `CLAUDE.md`.
    
    Then whenever Claude works on this project, it already knows them.
    
    ---
    
    But there's one thing you need to understand.
    
    `CLAUDE.md` gives Claude **instructions**. It doesn't technically block Claude from doing something.
    
    So if you write, "Never modify migration files manually."
    
    Claude should follow that rule, but it still technically has access to those files.
    
    If something absolutely shouldn't happen, that's where permissions, sandboxing and hooks come in.
    
    You'll get to those next.
    
    ## What's Filling Up While Claude Works?
    
    Before going further, you should understand the **context window**.
    
    This is basically the information Claude is working with during the current session.
    
    That includes:
    
    - your conversation
    - files Claude has read
    - terminal output
    - tool results
    - `CLAUDE.md`
    - other memory Claude has loaded
    
    And that context has a limit.
    
    So if you keep loading unnecessary information into it, you're using space and attention that Claude could be using on the actual task.
    
    That's also why `CLAUDE.md` shouldn't become some massive document.
    
    ## Why Should You Keep CLAUDE.md Short?
    
    As more and more information enters the context window, Claude has more things competing for its attention.
    
    You can think of it like an **attention budget**.
    
    Every line inside `CLAUDE.md` is using some of that budget because Claude keeps loading that file while working on your project.
    
    So don't put something there just because, "Maybe Claude might need this one day."
    
    Put things there because Claude should know them whenever it works on the project.
    
    You'll often see guidance around keeping `CLAUDE.md` well under 200 lines. But don't treat 200 lines as a target.
    
    If everything useful fits into 30 or 40 lines, that's even better.
    
    ## Where Does CLAUDE.md Live?
    
    There isn't only one place you can have it. Claude supports different levels of instructions.
    
    ### Personal Instructions
    
    You can have:
    
    ```
    ~/.claude/CLAUDE.md
    ```
    
    This applies across all of your projects.
    
    So if there's something you personally want Claude to follow everywhere, you can put it here.
    
    ### Project Instructions
    
    Inside your project, you can use:
    
    ```
    ./CLAUDE.md
    ```
    
    or:
    
    ```
    ./.claude/CLAUDE.md
    ```
    
    This is usually the one you'll use the most.
    
    For `atelier-store`, this is where you can keep things like:
    
    - your stack
    - commands
    - database rules
    - testing rules
    - storefront design rules
    
    You can also commit this file to Git, so everyone working on the project gives Claude the same project instructions.
    
    ### Local Project Instructions
    
    You can also have:
    
    ```
    ./CLAUDE.local.md
    ```
    
    This is for something that only applies to **you** on this specific project.
    
    Maybe you use a local test account. Maybe you have your own sandbox URL. Things like that can live here and normally stay out of Git.
    
    Claude can use instructions from all of these levels together.
    
    <aside>

    ## Wait, Doesn't Claude Already Have Memory?
    
    It does.
    
    Claude Code also has **auto memory**.
    
    The difference is simple.
    
    **`CLAUDE.md` is what you intentionally tell Claude.**
    
    **Auto memory is what Claude learns while working with you.**
    
    For example, maybe while working on `atelier-store`, Claude discovers some weird issue with your local setup. Or maybe you correct the same project-specific behavior a few times.
    
    Claude can save useful things like that so they can be used again in future sessions.
    
    Each project gets its own memory folder, with `MEMORY.md` as the main file.
    
    Claude can also create other memory files for more specific things.
    
    To see what's stored, run:
    
    ```
    /memory
    ```
    
    And to see what Claude actually has inside the current session, run:
    
    ```
    /context
    ```
    
    You may also see people start a message with `#` to tell Claude to remember something. By default, that goes into auto memory.
    
    It doesn't mean Claude is directly adding that thing to `CLAUDE.md`. If you specifically want something inside `CLAUDE.md`, tell Claude to add it there.
    
    ## What Should Actually Go in CLAUDE.md?
    
    A simple rule I like is, "**If removing this instruction would probably make Claude assume the wrong thing, keep it.**"
    
    Otherwise, ask whether Claude really needs it in every session.
    
    For example, inside `atelier-store`:
    
    ```markdown
    ## Commands
    
    - Package manager: pnpm
    - Start dev server: `pnpm dev`
    - Run tests: `pnpm test`
    - Typecheck: `pnpm typecheck`
    ```
    
    Later, once you add the database:
    
    ```markdown
    ## Database
    
    - Use Drizzle ORM for all database access
    - Database schema lives in `src/db/schema/`
    - Never write raw SQL unless specifically requested
    ```
    
    And once you set up the storefront design:
    
    ```markdown
    ## Storefront
    
    - Keep customer-facing pages editorial and product-focused
    - Reuse the existing design system
    - Avoid dashboard-style UI
    - No gradients
    ```
    
    Those are useful because they actually change how Claude should work.
    
    Now compare that with:
    
    ```
    Write high-quality code.
    Follow best practices.
    Make the UI beautiful.
    Keep everything clean.
    ```
    
    These sound nice, but they don't really tell Claude anything useful.
    
    Same with, "Make the storefront premium." What does that actually mean?
    
    Instead, you could say, "Use large product imagery, generous spacing and restrained controls on storefront pages."
    
    That's something Claude can actually follow.
    
    And don't dump your entire project structure or huge API documentation into `CLAUDE.md` either.
    
    Keep the things Claude should know **every time it works on this project**.

    ## Check Which Mode You're In

    ## What Are Permissions?
    
    Permissions let you decide what Claude can do automatically, what it should ask you about and what it shouldn't be allowed to do at all.
    
    There are three basic rule types, allow, ask, deny.
    
    - **Allow** means Claude can perform that matching action without asking you.
    - **Ask** means Claude has to stop and get your approval.
    - **Deny** means Claude Code blocks it.
    
    And if several rules match, Claude checks them in this order, **deny → ask → allow**
    
    So deny wins first.
    
    You can inspect the permissions for the current project with,
    
    ```
    /permissions
    ```
    
    You'll also notice that when Claude asks for permission, it can give you options such as approving something once or not asking again for that kind of action.
    
    That's useful because you probably don't need to approve, `pnpm build` for the fifteenth time.
    
    But you also shouldn't click **don't ask again** on everything without thinking about what you're allowing.
    
    ## Set Up Permissions for `atelier-store`
    
    Now let's decide what makes sense for this project. Claude will probably run commands like:
    
    ```bash
    pnpm build
    pnpm test
    pnpm typecheck
    git status
    git diff
    ```
    
    again and again.
    
    Those are normal development checks. You may want Claude to run them without stopping you each time.
    
    But `git push` is different. Maybe you always want to see that before it happens.
    
    And later this project will contain things like:
    
    ```
    DATABASE_URL
    BETTER_AUTH_SECRET
    STRIPE_SECRET_KEY
    ```
    
    inside environment files.
    
    Claude shouldn't be able to read those.
    
    You can keep project permission rules inside (create this file in the project folder):
    
    ```
    .claude/settings.json
    ```
    
    For example (add these rules in the project folder):
    
    ```json
    {
      "permissions": {
        "allow": [
          "Bash(pnpm build)",
          "Bash(pnpm test *)",
          "Bash(pnpm typecheck)",
          "Bash(git status)",
          "Bash(git diff *)"
        ],
        "ask": [
          "Bash(git push *)"
        ],
        "deny": [
          "Read(.env)",
          "Read(.env.*)",
          "Edit(.env)",
          "Edit(.env.*)"
        ]
      }
    }
    ```
    
    Now you've created a much more useful baseline. Claude can run the normal checks you expect.
    
    It still asks before pushing code. And your environment files are blocked from its normal file access.
    
    ## CLAUDE.md vs Permissions
    
    This is also where the difference from the previous lesson becomes clear.
    
    Inside `CLAUDE.md`, you could write, "Never read `.env`". Claude should follow that instruction. But it's still guidance you're giving the model.
    
    A permission rule is different.
    
    When something matches a `deny` rule, Claude Code itself blocks that action.
    
    So use `CLAUDE.md` for things like, "Use the existing design system when building storefront pages."
    
    Use permissions for things like, "Claude cannot read this file."
    
    `CLAUDE.md` tells Claude **how you want it to work**. Permissions decide **what Claude Code is actually allowed to do**.

If a deployment ever uses something guessable there, an attacker can forge those tokens, and CodeRabbit even traced the specific path: a forged change-email verification token that ends with the attacker owning the victim's account.
    
    Notice what kind of finding this is. There's no bug in our code today. It's a missing guardrail, and it becomes a real vulnerability the day someone deploys this with a lazy secret. Exploitability is marked difficult, but the impact is account takeover, which is why it's the one medium in the list.
    
    And there's a nice irony here. Our permission rules stop Claude from ever reading this secret. But nothing in the application ever checked whether the secret is any good.
    
    So bring it into Claude Code:
    
    > 🍿 CodeRabbit reported this security finding:
    > 
    > 
    > "The application accepts any explicitly configured BETTER_AUTH_SECRET, while the authentication dependency only warns about short or low-entropy values. A guessable shared secret allows attackers to forge authentication-related HS256 tokens."
    > 
    > Investigate whether this is accurate for our current Better Auth setup and explain the risk in the context of this application first. Don't modify anything yet.
    > 
    
    **[Recording note: show Claude's investigation summary briefly, then continue.]**
    
    Once Claude confirms it, let it fix it:
    
    > 🍿 Add startup validation for BETTER_AUTH_SECRET: the application must fail to start with a clear error unless the secret is at least 32 bytes of high-entropy material. Don't log the secret or any part of it in the error. Keep the check in one place where the auth configuration is created.
    >

    ### Finding 2: The Newsletter Form Leaking Emails
    
    The next finding is low severity but trivially real, and honestly, it's my favorite of the three.
    
    The homepage has a newsletter signup form. When Claude built that page back in the permissions lesson, it scaffolded the form with `action="#"` and no method. Placeholder code. But HTML has a default: a form without a method submits as GET. Which means every email address typed into that form gets appended to the URL, into the address bar, the browser history, and our server logs.
    
    Think about what just happened. AI-generated placeholder code, sitting on the homepage, quietly leaking subscriber emails. Nothing crashed. Nothing looked wrong. This is exactly the kind of thing an independent scan catches and a quick glance never does.
    
    The fix is small:
    
    > 🍿 The homepage newsletter form at src/app/page.tsx submits via default GET, which puts the entered email address into the URL. Convert it to a proper POST server action that accepts the email, and make sure no email value ever ends up in a URL. A simple success state is enough, we don't need a real mailing list integration yet.
    > 
    
    Verify it: submit the form, check the address bar stays clean, check the network tab shows a POST.
    
    ### Finding 3: The Judgment Call
    
    The last finding is signup email enumeration. Right now, signing up with an email that already has an account returns a specific error, while a new email succeeds. So anyone can probe our signup endpoint and figure out which email addresses have accounts on this store.

Apply the minimal configuration change, and add a short note in CLAUDE.md that full email verification is planned but not yet implemented.

- ✅ **05 | Skills and Reusable Workflows**
    
    At this point, you've already built several parts of `atelier-store`, and you're probably starting to notice something.
    
    The features change, but a lot of the process doesn't.
    
    When Claude builds another page, you still want it to inspect what already exists, reuse the design system, search for existing components, keep the page responsive, avoid unrelated changes, and verify what it built.
    
    You could keep writing all of that inside every prompt. Or you can teach Claude that process once and reuse it.
    
    That's what **Skills** are for.
    
    ## What Is a Skill?
    
    A Skill is a reusable procedure or piece of knowledge that Claude can load when it becomes relevant.
    
    At its simplest, a Skill is a folder containing `SKILL.md`. Inside that file, you describe what the Skill does and how Claude should handle that kind of work.
    
    You can call a Skill yourself, like `/build-ui`, or Claude can use it automatically when your request matches what the Skill is meant for.
    
    This is different from `CLAUDE.md`. Your `CLAUDE.md` loads into every conversation for this project. A Skill loads its full instructions only when it's actually needed. So a detailed UI workflow doesn't take up context while you're debugging a database migration.
    
    ## CLAUDE.md or Skill?
    
    Ask whether something is a **project fact** or a **repeatable process**.
    
    "Use pnpm. Use Drizzle. Reuse the existing design system." Those are facts, they belong in `CLAUDE.md`.
    
    But "inspect the implementation, find reusable components, build the UI, check responsive behavior, run the app, verify, typecheck, summarize" is a process. Claude only needs it when doing that kind of work. That's a Skill.
    
    - **Project fact → `CLAUDE.md`**
    - **Repeatable process → Skill**
    - **One-time task → just ask Claude**
    
    Anthropic specifically recommends Skills when you keep repeating the same instructions, or when something inside `CLAUDE.md` starts becoming a procedure rather than project context.
    
    ## Create a Skill for Building UI
    
    Project Skills live inside `.claude/skills/`. Create:
    
    ```
    .claude/
      skills/
        build-ui/
          SKILL.md
    ```
    
    The directory name becomes the command: `/build-ui`. Because this Skill is specific to `atelier-store`, keeping it inside the project means you commit it with the code and everyone gets the same workflow. A Skill for all your projects would live under `~/.claude/skills/` instead.
    
    A Skill has YAML frontmatter and Markdown instructions:
    
    ```markdown
    ---
    name: build-ui
    description: Build or update customer-facing ecommerce UI using the existing design system, components, product patterns and responsive conventions. Use when creating or significantly changing pages, sections or customer-facing components.
    ---
    
    Build or update the following UI:
    
    $ARGUMENTS
    
    Follow this process:
    
    1. Inspect the current implementation and related components.
    2. Search for reusable components before creating new ones.
    3. Reuse the existing design system and patterns.
    4. Keep the change focused on the requested feature.
    5. Verify responsive behavior.
    6. Run and visually verify the application.
    7. Run the normal project checks.
    8. Fix reproducible issues without expanding scope.
    9. Summarize what changed.
    ```
    
    `$ARGUMENTS` is whatever you type after the command, so the Skill carries the process and you only describe the feature.
    
    Notice we're not turning `SKILL.md` into a huge manual. It's focused. If it eventually needs large reference material or scripts, those move into separate files.
    
    ## The Description Is the Trigger
    
    This part matters more than it looks. The `description` isn't documentation for you. **It's how Claude decides whether the Skill is relevant.** Claude reads the names and descriptions of available Skills and matches your request against them.
    
    ```yaml
    description: Useful UI workflow.
    ```
    
    tells Claude nothing.
    
    ```yaml
    description: Build or update customer-facing ecommerce UI using the existing design system, components, product patterns and responsive conventions. Use when creating or significantly changing pages, sections or customer-facing components.
    ```
    
    tells Claude what the Skill does and when to use it. A weak description is the main reason a Skill doesn't trigger when you expect it to.

    You don't always have to type `/build-ui`. If you simply ask,

    Imagine you create `/deploy` or `/commit`. Those have real side effects. You probably don't want Claude deciding on its own, "Everything looks ready. I'll deploy it."

    ```yaml
    disable-model-invocation: true
    ```

    ```yaml
    user-invocable: false
    ```

    ## Skills Use Progressive Disclosure
    
    Another reason Skills scale better than stuffing `CLAUDE.md`: how they load.
    
    Three layers. First, Claude only sees the metadata, the name and description. When the Skill becomes relevant, it loads the `SKILL.md` instructions. And if the Skill has extra references, examples or scripts, those load only when necessary:
    
    ```
    build-ui/
      SKILL.md
      references/
        design-system.md
      scripts/
        verify-ui.sh
    ```
    
    The main `SKILL.md` doesn't need the entire design system inside it. It can point Claude to `references/design-system.md` when deeper guidance is needed. Anthropic calls this progressive disclosure.
    
    ## What Else Can a Skill Do?
    
    **[Recording note: rapid-fire beat, ~90 seconds, on-screen list, no demos. Each item is one sentence of VO.]**
    
    A few more controls worth knowing exist, and you'll reach for them as your workflows mature.
    
    A Skill can bundle **scripts** for the deterministic parts of a workflow, so the same mechanical steps run identically every time instead of being re-explained in prose. It can declare **allowed tools**, reducing permission prompts for tools the workflow obviously needs, though don't hand a Skill `Bash(*)` just for convenience. It can run in its **own forked context**, so a heavy review doesn't fill your main conversation. And it can specify which **model** and how much reasoning to use, or which file paths it's relevant to.
    
    You don't need any of that for `/build-ui`. Start simple, add controls when the workflow actually needs them.
    
    ## Build a Second Useful Skill
    
    Let's build something different: `/review-changes`.
    
    Create `.claude/skills/review-changes/SKILL.md`:
    
    ```markdown
    ---
    description: Review current implementation changes before they are accepted or committed. Use when checking a completed feature, reviewing the current diff or looking for regressions and unnecessary changes.
    ---
    
    ## Current diff
    
    !`git diff HEAD`
    
    Review the current changes against the requested feature and project instructions.
    
    Check:
    
    1. Whether the implementation actually solves the requested task
    2. Bugs or regressions
    3. Unnecessary changes
    4. Existing components or patterns that should have been reused
    5. CLAUDE.md violations
    6. Missing verification or tests
    
    Don't make changes yet.
    
    Return the important findings in order of severity.
    ```
    
    Notice the line with the exclamation mark. Skills can inject **live command output**: Claude Code runs `git diff HEAD` and inserts the result before Claude works with the Skill. So `/review-changes` always reviews your actual current diff, without you copying it into the prompt.
    
    Now after Claude finishes something, run:
    
    ```
    /review-changes
    ```
    
    and get the same review process every time.
    
    One habit worth building on top of it: switch to a **different model** with `/model` before running the review. You get a fresh second opinion instead of asking the same model to validate its own decisions. It's the same reasoning we used for CodeRabbit, applied inside Claude Code itself.
    
    That's a much more useful Skill than creating separate Skills for every individual page. You want to encode repeatable engineering processes.
    
    ## Skill Hygiene
    
    A few final things.
    
    You don't have to write every `SKILL.md` by hand. Anthropic has a **Skill Creator** workflow that builds and improves Skills through conversation, and it can even run evaluation cases with and without the Skill to check it actually improves Claude's behavior. Because a Skill that sounds good isn't necessarily a Skill that works. Test it.
    
    Don't turn `.claude/skills/` into a mess either. Every Skill adds metadata Claude has to consider. Ten useful Skills are fine; a hundred random ones aren't. `/skill-doctor` can inspect Skill usage and context cost to find the ones giving you nothing.
    
    And be careful with Skills you download. They can contain scripts, command execution and tool access, so read `SKILL.md` and any `scripts/` before installing. Treat executable code inside a Skill like any other code entering your development environment.
    
    Finally, keep `/build-ui` and `/review-changes` in the repository. Now another developer clones the application and gets the same workflows. The development process doesn't live only in your chat history anymore. It lives with the project.
    
    And don't try to design the perfect Skill on day one. Use it, watch where Claude still makes mistakes, and fix the Skill: add a missing rule, sharpen the verification step, fix a description that triggers at the wrong times. Skills improve from actual usage.

    Because before Claude builds the admin side, it needs to understand quite a few different areas of the application. Authentication. Products. Database schema. Inventory. Orders. Existing UI patterns.
    
    Claude could research all of that inside the main conversation. But then all of those file reads, searches and intermediate findings would fill the same context we're about to use to actually build the feature.
    
    That's where **Subagents** come in.
    
    ## What Is a Subagent?
    
    A subagent is another Claude agent that receives a focused task and works on it inside its own context.
    
    The main Claude delegates the task. The subagent investigates it. Then it reports the important result back.
    
    So instead of your main conversation carrying every file and every search the subagent needed, you mainly get back the useful findings. That's the real value.
    
    **Subagents give you context isolation.** They're not magically smarter versions of Claude. They're useful because some work can happen separately.
    
    ## Don't Think of Subagents as AI Employees
    
    This is where subagents sometimes get overcomplicated.
    
    People create things like, Senior Staff Backend Engineer, Elite Security Architect, World-Class React Expert. But Claude doesn't suddenly gain new knowledge because you gave the context window a fancy job title.
    
    The better question is, "What work can happen separately that my main conversation doesn't need to carry?"
    
    For our admin application, that's pretty obvious. Before implementing anything, we need several independent investigations. So let's delegate them.

        ## You Can Create Your Own Subagents Too
        
        The built-in agents are enough for a lot of work. But just like Skills, Claude Code also lets you create your own reusable subagents.
        
        And if you understood how Skills work in the previous lesson, this will feel familiar.
        
        A project Skill lives somewhere like, `.claude/skills/` , a project subagent lives inside `.claude/agents/` and is also defined using a Markdown file with frontmatter and instructions.
        
        So conceptually, they're quite similar.
        
        With a Skill, you define, "Here's a reusable process Claude should know how to follow." With a subagent, you're defining, "Here's a focused type of work Claude can delegate into a separate context."
        
        You can describe:
        
        - when the subagent should be used
        - what its job is
        - which tools it can access
        - which model it should use
        - how much reasoning it should do
        - what kind of result it should return
        
        For example, you might eventually create subagents for:
        
        ```
        investigating bugs
        researching an unfamiliar part of a large codebase
        security investigation
        architecture research
        checking a migration
        analyzing a legacy system
        ```
        
        The same advice from Skills applies here too. Don't create fifty agents just because you can.
        
        Create one when you notice a **repeatable type of work that benefits from having its own context**.
        
        I'm not going to go deeper into building custom subagents here because that's a whole topic on its own, and it's one of the things I cover properly inside the Agentic Engineering course.
        
        For this crash course, the important thing is understanding **why subagents exist and when they become useful**.

    ## More to Learn?
    
    So, is that everything you need to know about Claude Code?
    
    Definitely not.
    
    You just learned how Subagents let Claude split work into separate contexts so different parts of a problem can be investigated independently.
    
    But you can take that same idea much further.
    
    What if those agents don't just **investigate** different parts of the application? What if they start **building different features at the same time?**
    
    Claude Code has a solution for that too.
    
    You can combine agents with isolated **Git worktrees**, so each agent can work on its own copy of the repository while building features in parallel.
    
    And that's where you start getting into the more advanced side of Claude Code:
    
    - parallel feature development
    - Git worktrees
    - MCP
    - Hooks
    - deeper multi-agent workflows
    - complete production engineering workflows
    
    So Subagents are really just the beginning of that idea.
    
    You learned how to separate **context**. The next step is learning how to separate the **actual work** happening across multiple agents at the same time.
